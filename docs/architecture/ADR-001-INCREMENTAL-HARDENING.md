# ADR 001: Harden existing execution boundaries before expanding the OS

Date: 2026-11-10. Status: accepted for bounded repository implementation; host installation and release are not authorized by this ADR. Evidence: [current truth](../audits/CURRENT_SYSTEM_TRUTH.md), [risk register](../audits/SECURITY_RISK_REGISTER.md), [test baseline](../audits/BASELINE_TEST_RESULTS.md).

## Architectural implications

No additional runtime agents, services, database, vector store, provider or dashboard is justified. Existing SQLite state, domain services, registries, skills and MCP clients remain the architecture. This work does not implement a second orchestrator. Logical specialist ownership is documented in [capability matrix](../audits/CAPABILITY_MATRIX.md).

Security policy remains deterministic application responsibility. The corrected prompt contract describes the desired behavior, but cannot repair missing independent approval enforcement. Global instruction layers are configuration layers, not authority levels. External evidence stays untrusted.

The current SDK remains pinned below v2. A version upgrade has broad protocol/API implications and requires a separate compatibility batch rather than incidental dependency churn. See [MCP contract](MCP_PROTOCOL_CONTRACT.md). No mutation of canonical data or removal of legacy compatibility code is part of these decisions.

## Revisit conditions

Revisit after measured golden outcomes, explicit approval lifecycle tests, a clean deployment and a labeled retrieval benchmark. A new technology must improve a demonstrated bottleneck against the same workload, including CPU/memory and maintenance costs. Proposed targets are not current production guarantees.
