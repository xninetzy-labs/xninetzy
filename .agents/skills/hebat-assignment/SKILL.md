# HEBAT Assignment Foundation

This skill is the reusable foundation for **all HEBAT assignments**, regardless of course, lecturer, project theme, team structure, or assignment format.

Its purpose is to ensure that every HEBAT deliverable is:

* grounded in the actual HEBAT materials and assignment requirements,
* academically understandable and evidence-based,
* consistent in structure and visual design,
* ready for submission,
* reusable across different courses and project contexts.

The skill should prioritize **understanding before writing, structure before styling, and verification before delivery**.

---

## 1. Core Principles

### 1.1 Retrieve the authoritative assignment context first

Before designing or writing, collect the most relevant available materials:

1. HEBAT module or learning materials
2. Assignment brief
3. Lecturer instructions or course contract
4. Weekly progress requirements
5. Previous approved deliverables, when available
6. Required submission format and naming convention

Do not invent requirements that are not present in the available assignment context.

When multiple instructions conflict, prioritize:

**official lecturer/course instructions → assignment brief → HEBAT materials → general academic conventions.**

---

### 1.2 Build understanding before drafting

Before producing the final deliverable, understand the topic through the available knowledge sources:

* HEBAT materials
* Obsidian or personal knowledge base
* stored knowledge and memory, when appropriate
* project notes and prior work
* relevant academic literature
* credible web sources
* supporting datasets or field evidence

The goal is not to collect information indiscriminately, but to determine:

**What is the problem?
Why does it matter?
What is the relevant context?
What evidence supports the discussion?
What does the assignment actually require?**

---

### 1.3 Use a consistent planning structure

Before building the document, define:

**Input → Understanding → Argument → Evidence → Structure → Design → Build → QA → Submission**

Every assignment should have a clear relationship between its requirements and its final output.

---

## 2. General Assignment Workflow

Use this workflow for all HEBAT tasks:

### Step 1 — Retrieve

Collect the authoritative assignment context and supporting materials.

### Step 2 — Understand

Identify:

* theme
* learning objectives
* problem/context
* scope
* key concepts
* required methodology
* expected output
* evaluation criteria
* submission requirements

### Step 3 — Research

Use appropriate evidence from:

* HEBAT materials
* academic papers
* government or institutional sources
* official datasets
* field observations
* credible web sources

Do not add research simply for volume. Every source should support a meaningful claim, decision, or section.

### Step 4 — Plan

Create the logical structure before producing the final document.

At minimum, determine:

* introduction
* context/problem
* analysis/discussion
* methodology or process, when relevant
* findings/output
* conclusion
* references

Adapt the structure to the assignment rather than forcing every assignment into one template.

### Step 5 — Design

Establish the document structure and visual system before building:

* page hierarchy
* heading hierarchy
* typography
* spacing
* table style
* caption style
* figure treatment
* citation style
* page layout
* cover layout, when required

### Step 6 — Build

Produce the deliverable in the requested format.

For document-based assignments:

**DOCX → PDF → visual/structural QA**

### Step 7 — Verify

Check both content and presentation.

Verify:

* assignment requirements
* factual consistency
* citations
* headings
* page numbering, when applicable
* table/figure placement
* cover layout
* page overflow
* typography
* spacing
* links
* filename
* submission format

### Step 8 — Deliver

Provide the final submission-ready files and required links/materials.

# 3. Document Foundation

Unless the lecturer or assignment specifies another standard, use the following baseline.

## 3.1 Body text

* Font: Times New Roman
* Size: 12 pt
* Color: black `#000000`
* Alignment: justified
* Line spacing: 1.5
* Paragraph spacing: consistent throughout
* Widow/orphan control: enabled where supported
* No unnecessary decorative elements
* No em dash `—`

Use normal punctuation and sentence construction instead of relying on em dashes.

---

## 3.2 Heading hierarchy

Default hierarchy:

### H1

* 24 pt
* bold
* black
* used for major sections

### H2

* 16 pt
* bold
* black
* used for major subsections

### H3

* 13 pt
* bold
* black
* used for detailed subsections

Headings should be informative.

Prefer:

**2.5 Feasibility Analysis in the Surabaya Context**

instead of:

**2.5 Why This Is Easy**

Do not use unnecessary decorative prefixes such as:

**BAB I**, **BAB II**, etc.

unless explicitly required by the lecturer.

---

# 4. Cover Page

When a cover page is required, use a professional full-page composition.

## 4.1 Required information

The cover should normally contain:

* assignment/project title
* subtitle, when useful
* UNAIR logo, when required
* group/team or student identity
* lecturer name
* study program
* faculty
* university
* city
* year

The lecturer should be included whenever the course instructions require a lecturer field.

---

## 4.2 Title rules

Titles should:

* describe the actual project clearly,
* avoid unnecessary punctuation,
* avoid em dashes,
* avoid overly promotional wording.

Prefer:

**EcoTrack Platform for Sustainable Waste Management**

instead of:

**EcoTrack — A Revolutionary Waste Solution**

---

## 4.3 Group identity

For group assignments:

**Kelompok 4**

Do not automatically place a full member list on the cover unless required.

When a member list is required, use:

1. NIM Name
2. NIM Name
3. NIM Name

Do not use icons or decorative bullets for required academic identity information.

For individual assignments:

**Nama | NIM**

---

## 4.4 Lecturer field

Use:

**Dosen: Full Name, Academic Titles**

The lecturer name must come from authoritative course information such as:

* lecturer/course contract,
* HEBAT records,
* verified assignment materials.

Never guess the lecturer.

---

## 4.5 Default A4 layout

Unless another format is specified:

* Paper: A4
* Top margin: 2.3 cm
* Bottom margin: 2.3 cm
* Left margin: 2.5 cm
* Right margin: 2.5 cm
* No header/footer on the cover

The cover should fit exactly on one page.

When using the UNAIR logo, maintain a visually balanced vertical composition:

**title → logo → identity → lecturer → academic metadata**

Verify that the logo is visually centered and that the cover does not overflow to a second page.

---

# 5. Table of Contents and Section Titles

## 5.1 Table of contents

The TOC should contain only meaningful navigational information.

Do not include placeholder text such as:

> "The table of contents will be updated."

Make sure:

* headings match the document,
* numbering is consistent,
* page numbers are correct,
* indentation reflects heading levels.

---

## 5.2 Section titles

Use informative titles.

Prefer:

**2.5 In-Depth Research on the Surabaya Context and Implementation Feasibility**

instead of:

**2.5 Deep Research Surabaya**

Avoid em dashes in all headings and titles.

---

# 6. Content Quality Standard

Every section should answer a clear academic purpose.

A useful structure is:

**Claim → Explanation → Evidence → Interpretation → Relevance**

Avoid sections that simply stack quotations or facts without analysis.

The writing should demonstrate:

* understanding,
* reasoning,
* connection between evidence and claims,
* application of course concepts,
* relevance to the project/problem.

Avoid writing that sounds like a collection of disconnected summaries.

---

# 7. Research and Evidence

Use sources according to their authority and relevance.

## Preferred source hierarchy

1. Official government/institutional sources
2. Peer-reviewed academic research
3. Official organizational documentation
4. Credible datasets
5. Professional or industry sources
6. Reputable secondary sources

Avoid relying heavily on:

* anonymous websites,
* low-quality blogs,
* unsupported claims,
* search snippets as primary evidence.

When a claim materially affects the assignment, support it with an appropriate source.

---

# 8. Tables, Figures, and Captions

## Tables

Default table style:

* fixed layout
* readable column widths
* header background: `#D9D9D9`
* black text
* consistent borders
* no excessive decoration

Use tables when they improve comparison, organization, or clarity.

---

## Figures

Every important figure should have:

* figure number,
* informative caption,
* source, when applicable,
* sufficient resolution,
* clear relationship to the surrounding discussion.

Default caption:

* 9 pt
* italic
* gray

Example:

*Figure 3. User journey mapping for household waste disposal*

---

# 9. Links and External Artifacts

When the assignment uses external artifacts such as:

* Figma
* Google Sheets
* prototype links
* datasets
* project repositories

keep the relevant links in the final document.

Do not surround useful links with unnecessary technical metadata.

A simple format is preferred:

**Figma Prototype:** [link]

**Project Spreadsheet:** [link]

---

# 10. Conclusion Standard

The conclusion must synthesize the **entire discussion**, not simply repeat the introduction.

A strong HEBAT conclusion should connect:

**Theme → SDGs/context → problem → scope → research → methodology → analysis → proposed output → feasibility**

Explain why the selected theme or solution is appropriate based on the evidence.

When relevant, explain practical feasibility using contextual factors such as:

* relevance to everyday problems,
* availability of potential respondents,
* accessibility of field information,
* existing ecosystem or infrastructure,
* realistic implementation conditions.

The conclusion should emphasize **understanding and application of principles**, not merely compare tools or software.

---

## 10.1 Preferred conclusion opening

Avoid:

> "This practical assignment aims to train students..."

Prefer:

> "This practical assignment applies an understanding of..."

The conclusion should focus on what was learned, analyzed, developed, and demonstrated.

---

## 10.2 Required closing direction

Where applicable, end with concrete next steps such as:

* maintaining project data in the designated spreadsheet,
* finalizing the team PDF,
* updating the prototype,
* submitting the required Figma link,
* completing the required HEBAT submission process.

---

# 11. References

Use an informative reference section rather than a list of filenames.

Default title:

# DAFTAR PUSTAKA DAN SUMBER RUJUKAN TERKAIT

When useful, organize sources into categories.

### Modul & Materi HEBAT

Course modules, lecture materials, assignment briefs, and official HEBAT references.

### SDGs, Policies & Institutional Sources

United Nations SDGs, government regulations, institutional reports, and official policies.

### Academic Research & Prototypes

Academic papers, journals, conference publications, case studies, and relevant prototypes.

### Field Data & Local Context

Interviews, observations, local datasets, surveys, and Surabaya-specific evidence.

---

## 11.1 Informative reference labels

References should communicate what the source contributes.

Prefer:

**[S1] Design Thinking for Residential Waste Management in Taman Sasana Patra — Syntax Idea, 2024 — empathize-stage evidence from waste collection context**

instead of:

**[S1] Minggu ke 03 Tema Proyek.pdf**

The reference list should help the reader understand **why the source matters**, not merely identify the file.

---

# 12. Academic Tone

Use language that is:

* clear,
* precise,
* academically appropriate,
* readable,
* evidence-based,
* direct.

Avoid:

* excessive jargon,
* exaggerated claims,
* marketing language,
* unsupported superlatives,
* repetitive statements,
* overly complicated sentence structures.

Write for comprehension first.

---

# 13. Visual Design System

The visual system should support academic readability rather than compete with the content.

Default principles:

* consistent typography,
* consistent spacing,
* restrained use of gray/black,
* clear hierarchy,
* sufficient whitespace,
* aligned elements,
* consistent tables and figures,
* no unnecessary decorative graphics.

For academic deliverables, **clarity > decoration**.

---

# 14. Quality Assurance

Before delivery, perform at least two QA passes.

## Content QA

Verify:

* every assignment requirement is addressed,
* concepts are correctly understood,
* claims are supported,
* sources are relevant,
* citations are consistent,
* conclusion reflects the discussion,
* required links are present.

## Visual QA

Verify:

* cover is exactly one page when required,
* logo is correctly positioned,
* no unexpected blank pages,
* no text overflow,
* headings are consistent,
* tables are readable,
* figures are not cropped,
* captions remain with their figures/tables where possible,
* page breaks are intentional,
* font and spacing are consistent.

For generated documents, render and inspect the final PDF instead of trusting the DOCX source alone.

---

# 15. Submission Readiness

Before submission, verify:

**Content**

* assignment requirements satisfied
* evidence checked
* conclusion complete
* references complete

**Document**

* correct format
* correct filename
* correct page structure
* correct identity information
* correct lecturer information

**Artifacts**

* required spreadsheet updated
* prototype link accessible
* PDF generated
* supporting files complete

**Submission**

* destination identified
* required channels followed
* group/individual submission rules followed

---

# 16. General Submission Rule

When assignment instructions specify different submission destinations, follow them exactly.

Example logic:

**Group assignment**
→ submit according to the group submission channel
→ provide the required artifact to the designated administrator/person

**Individual assignment**
→ submit to HEBAT
→ provide the required copy to the designated administrator when instructed

Do not assume that every assignment uses the same submission route.

---

# 17. Reusability Rule

This skill must remain **course-agnostic**.

Do not hard-code:

* one course code,
* one lecturer,
* one project theme,
* one SDG,
* one methodology,
* one submission channel,
* one Figma structure.

Instead, dynamically retrieve those values from the relevant assignment context.

The foundation defines **how the assignment should be handled**, while course-specific materials define **what the assignment requires**.

---

# 18. Decision Rule

When uncertain, follow this priority:

**Official requirement**
→ **Assignment brief**
→ **Course/HEBAT material**
→ **Verified project context**
→ **Academic best practice**
→ **General formatting defaults**

Never let a generic formatting rule override an explicit lecturer requirement.

---

# 19. Standard Operating Principle

The complete HEBAT process is:

**Retrieve → Understand → Research → Plan → Design → Build → Verify → Submit**

The final deliverable should be:

**academically grounded, logically structured, visually consistent, technically verified, and submission-ready.**

This foundation is intentionally general so it can be reused across **all HEBAT courses and assignment types** without requiring manual rewriting of the core workflow.
