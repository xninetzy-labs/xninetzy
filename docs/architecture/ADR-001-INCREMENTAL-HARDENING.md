# ADR 001: Harden existing execution boundaries before expanding the OS

## Increment: FAISS publication and MCP lifecycle, 2026-11-15

Verified problems: replay appended duplicate vectors, separate index/map saves
could be acknowledged despite failure, corrupt projections were auto-rebuilt,
and the MCP entrypoint did not own an explicitly enabled projection loop.
Regression tests reproduce each problem; Phase3 records red/green/runtime evidence.

Decision: retain canonical SQLite/outbox and existing CPU FAISS APIs. Publish two
checked index/map slots through an atomic versioned pointer, deduplicate by key
and text fingerprint, fence model/generation/canonical freshness and preserve
legacy state for reviewed rebuild. Start the existing loop through MCP lifespan
only with an additional off-by-default flag; shutdown releases only undispatched
owned work and observes entered work cooperatively.

Alternatives: retaining independent overwrite saves leaves the reproduced crash
boundary; adding a vector database or storing full FAISS blobs in SQLite adds
infrastructure/migration without a demonstrated benefit. A full durable scheduler
would exceed this verified lifecycle gap. No alternative is adopted solely for
feature count.

Benefits: replay correctness, truthful failure and optional runtime ownership
without new services/providers/tables. Costs: two disk snapshots, index clone
RAM/copy work and integrity scans; measured CPU/RSS/large-corpus latency remain
unknown. POSIX cooperating writers and a trusted local directory are required;
hashes are not authentication. Old vector files remain preserved but are held
until reviewed rebuild; old runtime rollback cannot consume the new snapshot.
Canonical public tools/signatures stay compatible, except the separately corrected
three pure validator policies now remove false mutation-key/approval requirements.
Roll back only with the worker stopped and all projection files preserved.

Test strategy: actual FAISS, publication faults, thread/process replay, corruption,
embedding identity, stale canonical evidence, lease/shutdown fencing, real STDIO
restart and frozen installed parity. Three-node cached-model smoke is not a
retrieval-quality dataset or production-readiness proof. No owner index or host
configuration was modified. FINAL actions remain independently held.

Date: 2026-11-10. Status: accepted for bounded repository implementation; host installation and release are not authorized by this ADR. Evidence: [current truth](../audits/CURRENT_SYSTEM_TRUTH.md), [risk register](../audits/SECURITY_RISK_REGISTER.md), [test baseline](../audits/BASELINE_TEST_RESULTS.md).

## Decisions and alternatives

Graph continuation2026-11-15: old claim snapshots and ID-only acknowledgements let stale workers overwrite reclaimed processing state; canonical revision changes and incomplete edge payloads could also make projection markers inaccurate. Reuse existing attempts/lease/version/hash fields. Finalize only an unexpired matching processing claim, atomically commit marker updates against the exact active canonical snapshot, and source edge weight/properties from canonical rows with active endpoints. Unknown operations fail with bounded attempts; canonical updates clear obsolete markers. Provider/auth failure logs contain types or fixed safe ACK failures only.

Alternatives were a new lease-token schema/queue, distributed lock infrastructure, or continuing ID-only writes. Existing monotonic attempt plus exact lease comparison avoids migration; a nonblocking local POSIX file lock serializes cooperating updated tick execution without holding a SQLite transaction across network work. This fits one trusted local canonical database, not multi-host/NFS/mixed-version or hostile same-owner execution. Existing internal finalizers lacking a matching claim now return false. Public tools remain unchanged; stats add lost/deferred counts only when applicable. Added local IO/check/serialization cost is NOT_MEASURED, with no extra model call or runtime dependency. Canonical SQLite remains independent of optional services.

Validation uses actual SQLite lease takeovers, callback-time canonical changes, concurrency/poison/privacy tests and a fresh graph-only non-editable installation against the already supported official Neo4j5.26 image. The test backend has an internal bridge/no published host ports, bounded resources and ephemeral authentication/data; cleanup uses only owned resource IDs. Live resync/outage/retry/deletion is verified, while FAISS is explicitly stubbed and not certified. Optional graph-only CI is separate from the base wheel. [Neo4j driver query semantics](https://neo4j.com/docs/python-manual/current/query-simple/) and [SQLite transaction constraints](https://www.sqlite.org/lang_transaction.html) support scoped ACKs and short transaction boundaries. No external exactly-once, automatic worker startup, full graph reconciliation or owner rollout is claimed. Rollback preserves canonical/outbox evidence and requires reviewed runtime versions; never force recovery by resetting attempts, unlinking active locks or wiping projections.

Backup continuation2026-11-15: existing v1 verification accepted empty/incomplete manifests, did not check SQLite structure, and retention trusted manifest-supplied `path`/`name`. Restore copied files independently of that manifest and lacked a safety snapshot. Reproductions use only disposable state, including baseline retention deleting a synthetic unrelated directory. Keep the existing service/API and v1 file layout; validate exact required files, sizes/hashes, SQLite integrity/foreign keys and absence of symlinks/SQLite sidecars. Derive retention targets from actual direct child directories and explicitly preserve the newly published snapshot even within the same second. Manifests are not an authenticated source or permission grant.

Restore decision: require the existing local operator acknowledgement, an offline database with no journal sidecars, private verified staging and a verified pre-restore snapshot without pruning. Use a local POSIX lock for cooperating restores, fsync copied files/directories and replace canonical SQLite last. A raw private capture of the already offline current database avoids opening its WAL-format original read-only and creating sidecars during safety backup; SQLite validates that private capture. The owner must stop every participating reader/writer; lock probes cannot detect all idle file handles. No process is stopped automatically, and no boolean is promoted into independently authenticated approval.

Alternatives: accepting checksums alone permits corrupt but checksum-matching SQLite; deleting journals hides unresolved state; silently keeping vectors leaves mismatched projections; replacing the subsystem with a new backup framework adds dependencies without demonstrated value. Selected changes use stdlib and existing SQLite/files, no schema migration or provider. Cost is additional full file hashing/copying/integrity scans on explicit backup/restore; latency/RSS/CPU delta NOT_MEASURED. The online backup-copy loop has a cooperative30-second limit, not an overall IO or fsync deadline. [SQLite backup API](https://www.sqlite.org/backup.html), [integrity checks](https://www.sqlite.org/pragma.html#pragma_integrity_check) and [SQLite corruption guidance](https://www.sqlite.org/howtocorrupt.html) support distinguishing online snapshots, offline replacement and journal/handle safety. SQLite plus FAISS is not one atomic transaction; live graph/vector reconciliation and external effects after a point-in-time restore remain separate gates. On interruption preserve safety evidence and keep services offline. Rollback restores reviewed code hunks only; reverting these guards reinstates reproduced defects. Never downgrade to force a held restore or remove journals/locks automatically.

Workflow continuation2026-11-15: resume rebuilt a new plan from the previous message, completed actions could run twice, checkpoint errors were ignored, and cancellation/context races allowed further effects. Reuse the existing ordered executor and SQLite tables, with a versioned typed state envelope in existing JSON, immutable plan/owner/objective checks, short atomic checkpoint transactions and a nonblocking local POSIX file lock. Commit RUNNING before each effect and result/state before optional notification; retain successful evidence and hold uncertain mutation. Resume retries only a fixed read-oriented whitelist under current effective policy. No table/column, tool, dependency, framework or queue is added.

Alternatives: a thread-only lock cannot coordinate separate local MCP processes; a long SQLite transaction over a handler blocks unrelated writers; a time-expiring lease cannot safely allow takeover while a synchronous effect may still run; a new durable queue adds infrastructure before a verified need. The local OS lock fits the supported single-owner local deployment. [Python fcntl](https://docs.python.org/3/library/fcntl.html) documents Unix/nonblocking file locking; [SQLite](https://www.sqlite.org/lang_transaction.html) documents the single-writer and immediate-transaction constraints. This is a scoped design inference validated by real process/SQLite fixtures, not a multi-host/NFS or arbitrary same-owner writer security guarantee.

Cost: one small state serialization/hash and short SQLite step commits plus an advisory lock descriptor per running workflow; intermediate checkpoints are capped at256KiB. CPU/RSS/latency deltas are NOT_MEASURED. Current59 workflow cases cover real fixture-process interruption, concurrency, checkpoint rollback, cancellation, context, privacy and legacy failure modes; installed-MCP recovery verifies the packaged boundary. Compatibility: names/parameters remain, result checkpoint/cancelled status is additive; insufficient historical state is held rather than replanned. All participating executors must be updated; mixed old/new versions do not coordinate. Rollback preserves JSON/ledgers and holds resume instead of using the old duplicating implementation. No external exactly-once, universal domain verification or positive approval claim follows. See [contract](AGENTIC_WORKFLOW.md) and [Phase3](../implementation/PHASE_3_REPORT.md).

Internal approval continuation2026-11-14: reproduced service-level display-name/ID consent and reusable legacy approved rows, plus HEBAT domain owner/boolean shortcuts. Continuing those checks would leave an internal route around MCP containment. A new model argument, local secret readable by the same agent or automatically approved inbox record would not provide an independent trust boundary. The accepted bounded decision is to hold public approval and legacy execution validation, preserve rows/contracts, remove owner/boolean shortcuts and retain the atomic transition kernel as an explicitly non-authenticating internal primitive. Cost: operations remain unavailable; no migration, new database or service; negative and pure-kernel regression coverage is separate. Future positive issuance must bind verified principal, exact operation/payload/target, scope, expiry and single-use execution/reconciliation. It needs reviewed host/user interaction, not a forged scalar parameter.

The official [MCP security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) distinguishes consent and authority boundaries. [Elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) provides a client-mediated interaction mechanism with capability negotiation, not proof that every installed host presents an appropriate owner approval UI. It remains a candidate for a separately verified integration. No host approval, SDK upgrade or live user consent is claimed here.

Installed-wheel continuation: a source-only Docker copy changed while uv reused a cached local-project wheel; installed code failed the new service denial assertion from `/tmp`. Alternatives: discard the entire dependency cache, extend project-wide cache-key globs, or force own-package reinstall and compare installed runtime files. Choose the latter: existing frozen lock/dependency cache stays intact; own package is rebuilt and663 Python/JSON/SQL files are checked at build and in an isolated runtime. Missing/changed/extra code and source shadowing fail, with only the existing source-test manifest exclusion applied. No per-request cost; build-time CPU/I/O added, performance delta NOT_MEASURED. This follows uv's documented [local dependency cache behavior](https://docs.astral.sh/uv/concepts/cache/). Rollback must not silently restore a stale artifact; rebuild and verify any proposed older source before use.

## Architectural implications

November14 Phase1 decision: reuse the existing MCP adapter as the deterministic execution boundary and package a versioned explicit571-name risk catalog. Alternatives were continuing name heuristics, adding a second execution service, or implementing a model-issued approval token. The catalog plus existing SQLite reservations closes the reproduced downgrade/replay paths with no new runtime service, database or LLM call. Unknown policy fails closed, global/explicit owner restrictions remain authoritative, and consequential operations stay unavailable until independent approval exists. HTTP is likewise held without owner authentication. This trades unsafe legacy-call compatibility for explicit security, while preserving names and business parameters; WRITE schemas gain a required-at-execution key. Added CPU work is bounded validation/hashing/SQLite transactions; before/after latency/RSS impact is NOT_MEASURED. Typed output, privacy, timeout/concurrency, mismatch/restart and wire checks are required. Rollback preserves both legacy and gateway-v1 reservations; no destructive migration is accepted.

Learned config previously assigned arbitrary Settings fields, including credentials, permissions and the canonical database path. The accepted repair is a bounded numeric tuning allowlist shared by write/load/rollback and a read-only optional override reader. Alternatives were disabling all tuning or trusting approved proposal text. Protected legacy rows remain stored but inert; cache mutation follows durable commit. No owner setting/database was changed. This corrects permission/data-selection risk with constant-size filtering and no framework addition.

No additional runtime agents, services, database, vector store, provider or dashboard is justified. Existing SQLite state, domain services, registries, skills and MCP clients remain the architecture. This work does not implement a second orchestrator. Logical specialist ownership is documented in [capability matrix](../audits/CAPABILITY_MATRIX.md).

Security policy remains deterministic application responsibility. The corrected prompt contract describes the desired behavior, but cannot repair missing independent approval enforcement. Global instruction layers are configuration layers, not authority levels. External evidence stays untrusted.

The current SDK remains pinned below v2. A version upgrade has broad protocol/API implications and requires a separate compatibility batch rather than incidental dependency churn. See [MCP contract](MCP_PROTOCOL_CONTRACT.md). No mutation of canonical data or removal of legacy compatibility code is part of these decisions.

## Revisit conditions

November14 bounded decisions: an unconditional status update after a pending SELECT permits duplicate auto-execution and stale decision overwrite. Alternatives were holding BEGIN IMMEDIATE across action execution, adding a new queue/approval schema, or a conditional pending UPDATE with rowcount. The latter reuses SQLite, commits before the effect, adds no dependency/schema and preserves completed duplicate acknowledgement; stale decisions and missing outcomes now fail truthfully. Five fixture tests and125 related tests pass. It does not solve authenticated approval issuance or validation-only external replay. Runtime cost/throughput changes are NOT_MEASURED.

OpenCode2.2.6's native add output and official documentation establish mcp.servers/disabled. Keeping the old flat map loses discovery; rewriting all owner servers would exceed the verified problem. The accepted adapter migrates only Xninetzy, preserves effective disabled-owner policy, rejects conflicts and keeps Kilo's distinct format. Two host files have protected backups;16 configuration tests and9 SDK probes pass. Native isolated OpenCode health remains UNKNOWN despite this correction, so no host-parity claim follows. OpenCode1.x needs a separately verified profile rather than assuming2.x configuration is backward compatible. Sources/evidence and rollback are in CLIENT_CONNECTIONS.md and Phase 1.

Revisit after measured golden outcomes, explicit approval lifecycle tests, a clean deployment and a labeled retrieval benchmark. A new technology must improve a demonstrated bottleneck against the same workload, including CPU/memory and maintenance costs. Proposed targets are not current production guarantees.
